# Tutorial: Hacking Travel Booking Platform via Broken Access Control (IDOR → Zero-Click ATO)
**#cybersecurity #infosec #bugbounty #brokenaccesscontrol #idor #appsec**  
*By Zlatan H. (Summarized & Structured for Quick Revision & Deep Understanding)*

### Introduction
**Relying only on JWT tokens** for API security is **dangerous**.  

A real bug bounty case showed a critical **Broken Access Control** (IDOR) flaw in a travel booking platform. By changing one parameter (`customer_id`), an attacker could silently overwrite a victim's email address, leading to **full Account Takeover (ATO)** with zero interaction from the victim.

**Core Lesson**: Never trust client-supplied identifiers. Always validate ownership on the server side using the authenticated session/JWT context.

---

### 🧠 Core Concept (Memorize This)
- **IDOR (Insecure Direct Object Reference)**: Application uses user-supplied ID to access/modify objects without checking if the user owns that object.
- JWT authenticates the request but **does not enforce authorization** on the target resource.
- Result: Horizontal privilege escalation → Full Account Takeover.

**Impact**: Attacker changes victim’s email → Triggers password reset to attacker’s email → Complete control.

---

### 🛠️ Step-by-Step Exploitation

**Steps to Reproduce (Exam + Practical Ready)**:

1. **Login as Attacker** (e.g., Account with `customer_id=217`).
2. **Intercept Profile Update Request** using Burp Suite (or any proxy).
3. **Original Payload** (example):
   ```http
   POST /api/profile/update
   Authorization: Bearer <your_jwt_token>

   customer_name=Attacker&customer_email=attacker@test.com&customer_id=217
   ```
4. **Modify the Request** (Key Attack Step):
   - Change only `customer_id` to victim’s ID (e.g., `218`).
   - Keep the same JWT token and Authorization headers.
   ```http
   customer_name=Attacker&customer_email=attacker@test.com&customer_id=218
   ```
5. **Forward** the request → Server returns **HTTP 200 OK**.
6. **Result**: Victim’s email is now overwritten with attacker’s email.
7. **Finish ATO**: Trigger password reset on victim’s account → Reset link goes to attacker’s email.

---

### Impact Summary (High Severity)
- **Zero-Click Account Takeover**
- No victim interaction required
- Works because server trusted client-supplied `customer_id`
- Common in travel, e-commerce, and booking platforms

---

### 🛡️ Remediation (Defender Side - Must Know for Exams)

| Issue                        | Fix (Best Practices) |
|-----------------------------|----------------------|
| Client-supplied Object ID   | Always validate ownership using session/JWT user ID |
| Missing Authorization Check | Enforce server-side check: "Does this JWT belong to this customer_id?" |
| Over-reliance on JWT        | JWT = Authentication only. Authorization must be separate & strict |
| Profile Update Endpoints    | Use `PUT /api/profile/me` (use "me" or session identity, never user ID from body) |

**Golden Rule**: 
> **"If the user didn't authenticate as the owner of the object → Deny the operation."**

---

### Quick Revision Mnemonics
- **IDOR + JWT** = **Silent ATO**
- **Attack Flow**: Login (Attacker) → Intercept Update → Change `customer_id` → Overwrite Email → Password Reset → Takeover
- **Defense Formula**: Auth (JWT) + Authz Check (Ownership Validation) = Secure
- **One-Line Lesson**: Never trust `customer_id`, `user_id`, `account_id` from client without server-side verification.

---

### Why This Matters (Exam/Interview Points)
- Classic **Broken Access Control** (OWASP Top 10 #1).
- Shows difference between **Authentication** (JWT) and **Authorization**.
- Real-world impact in high-value targets (travel platforms handle payments & PII).
- Bug bounty favorite — Simple but devastating.
